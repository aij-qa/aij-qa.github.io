About

Quality strategy first, then the automation to carry it.

I own quality end to end for the Scrum team that ships customer solutions on a retail POS (point of sale) platform every sprint. I represent QA in planning, refinement and release go or no-go decisions, and I report quality metrics to the CTO, the product lead and the QA manager.

When our POS projects had no end-to-end process and no CI for tests, I took it on. I split the test cycle into jobs, gave each job an AI agent, and connected the agents to the real system through a server I built. One customer project went from no E2E tests to full E2E in one sprint.

Before retail POS, I tested ERP, pharma, port logistics, smart-factory, learning management and e-commerce systems.

Approach

Shift-left QA

Find problems at the requirement and design stage, before they become bugs.

Automation

Agentic automation

AI agents with clear jobs, limited tools and checks between every step.

Measurement

Data-driven quality

People

Team leadership

Agentic QA system

Six agents, one job each, in strict order.

A Testmo test case goes in. A reviewed, passing Playwright test and a Testmo report come out. Each agent checks its own work before the next one starts. Seven more agents and eight skills (workflows that run the agents in order) cover test design, PR review, failure triage and release reporting.

01

Scout

pom-scout

Maps each manual step to existing page objects and lists what is missing.

02

Builder

pom-builder

Adds only the missing methods. Never edits an existing one.

03

Generator

test-generator

Writes the spec and test data from the case and the project rules.

04

Runner

pos-runner

Runs on a Docker POS and fixes timing until it passes in a row.

05

Reviewer

review-runner

Every expected result needs an assertion. No fixed waits.

06

Reporter

report-generation

Final run, Testmo upload and the HTML report.

52ViKING Retail POS: Agentic E2E Automation

I designed and built the end-to-end test automation for the same POS: AI agents that write, run, review and report Playwright tests, a role-based MCP server, a POS that runs in Docker and the Jenkins CI. I lead the full automation process, with the planning and task delegation on me, and I moved Standard, Europris and Flugger from manual regression to E2E single-handedly.

  • Moved Standard, Europris and Flugger from manual regression to E2E single-handedly
  • Core product suite plus customer suites for Europris and Flugger
  • One shared project template, so every customer gets the same structure and CI
  • PR builds run the changed tests, and nightly runs cover the full suite
2 wk → 4 drelease cycle, Europris
30–50 hmanual regression per release, shrinking with E2E
4projects in CI

The challenge

The POS projects had no end-to-end test process and no CI for tests. Each monthly Standard release took 30–50 hours of manual regression, and each customer project needed its own 30–50 hour regression when required, depending on its case volume and test areas. Each customer project also had its own setup.

How it works

  • Six pipeline agents. A scout maps the manual test steps onto existing page objects, a builder adds the missing ones, a generator drafts the spec and test data, a runner runs it on the Docker POS until it passes 3 times in a row, a reviewer removes fixed waits, hard-coded data and weak assertions, and a report agent uploads the run to Testmo.
  • Role-based MCP server. 9 roles, each with its own token. An agent gets only the tools its role needs, a call outside the role is refused, and secrets are removed from every output. No tool can delete a project or push code: people do every commit.
  • POS in Docker. The POS and a debug browser run in containers, with a VNC view to watch a run live. Up to 3 POS instances run side by side.
  • Jenkins CI. PR builds run only the tests a change touches, images are reused when nothing changed, and locks stop two builds from sharing a POS. Each customer has a nightly full-suite slot with Testmo upload, an HTML report, email and a diagnostics file on failure.
  • Golden master checks. Receipts and transactions are compared with approved baselines, so a changed receipt line is caught.

The result

Europris moved to E2E, and its release cycle went from 2 weeks to 4 days. One customer project went from no E2E tests to full E2E in one sprint. The other projects are on the way, and the manual regression hours keep going down as more cases move to E2E and CI.
